# تقرير مراجعة Workspace — مقارنة النص بالملفات المنشورة

## نطاق المراجعة

تمت مراجعة الرابط النهائي فعليًا، وليس النسخة المحلية فقط. جرى فحص الشجرة، أسماء الملفات، التوثيق، جدول الأرجل، كودي Arduino وESP32، ملفات Wokwi وTeX، ومجلد Dashboard. النتيجة: الرابط منظم ولا يحتوي على ZIP أو `Original` أو `Backup` أو `assets`، لكن بعض المتطلبات موجودة في صورة شرح أو هيكل أولي فقط وليست تنفيذًا مكتملًا.

## ما تم تنفيذه فعلاً

### التنظيم
الرابط يحتوي على مجلدات واضحة: `docs` و`hardware` و`firmware` و`libraries` و`simulation` و`web-dashboard`. تم فحص الشجرة recursively، ووجدت 30 ملفًا، 29 منها نصية. لم يظهر داخل الرابط أي ملف ZIP أو اسم يحتوي `Original` أو `Backup` أو `assets`.

### التوثيق
تم توسيع `docs/README_AR.md` ليشمل فكرة المشروع، المسار الحرج للاتزان، الأنماط الأربعة، ترتيب القراءة، المكونات، PID، Dashboard، HC-SR04، receiver، السلامة، وقاعدة النسخة النهائية. كما توجد:

- `ENGINEERING_BLUEPRINT_AR.md`
- `OPERATING_PROCEDURE_AR.md`
- `VALIDATION_CHECKLIST_AR.md`
- `CHANGELOG_AR.md`
- `hardware/PINOUT_AND_POWER_AR.md`
- `hardware/RECEIVER_OLD_REUSE_AR.md`

هذه الملفات تشرح معظم الأفكار الواردة في النص، لكنها لا تحولها وحدها إلى كود قابل للتشغيل.

### الأنماط الأربعة
الأنماط الأربعة موضحة في README وBlueprint: USB Direct، Arduino + ESP32 Bridge، Arduino Standalone، وESP32 Standalone. فكرة فصل الأسلاك فيزيائيًا للنمط الرابع موثقة بشكل صحيح.

### الطاقة والـ receiver
تم توثيق GND المشترك، فرق 5V/3.3V، L298N، المحركات على التوازي، receiver القديم، IR، FD650، مقاومات LEDs، واحتياج HC-SR04 إلى Level Shifting عند ESP32.

## ما لم يُنفذ أو ما يزال ناقصًا

### 1. لا يوجد كود موحد باستخدام `#ifdef`
النص طلب ملفًا موحدًا يحتوي على:

- `#ifdef ARDUINO`
- `#ifdef ESP32`
- تبديل النمط من Pin في ESP32.

لكن الرابط يحتوي على ملفين مستقلين:

- `firmware/arduino/ArduinoBalance.ino`
- `firmware/esp32/ESP32Standalone.ino`

لا يوجد `#ifdef`، ولا يوجد ملف واحد يجمع المنطقين، ولا توجد دالة تبديل فعلية بين Bridge وStandalone.

### 2. ESP32 لا يبدّل بين النمطين
في `ESP32Standalone.ino` يوجد:

```cpp
#define MODE_PIN 35
```

لكن البرنامج لا يقرأ `MODE_PIN` داخل `setup()` أو `loop()` ولا يغيّر سلوكه بناءً عليه. لذلك شرط LOW = Bridge وHIGH = Standalone غير منفذ.

### 3. ESP32 Bridge غير موجود
لا توجد في كود ESP32:

- تهيئة Wi‑Fi فعلية.
- `WiFi.begin()` أو فحص الاتصال.
- UART مخصص للـ Bridge.
- قراءة أوامر من Dashboard وتمريرها إلى Arduino.
- استقبال Telemetry من Arduino.
- محول بروتوكول بين الأمر اللاسلكي وSerial Arduino.

وجود `#include <WiFi.h>` وحده لا يعني أن Wi‑Fi منفذ.

### 4. Cloud Backend وDashboard غير منفذين
مجلد `web-dashboard` يحتوي README من بضعة أسطر فقط. لا توجد ملفات:

- HTML.
- CSS.
- JavaScript.
- Node.js server.
- MQTT client أو broker configuration.
- WebSocket server.
- Authentication.
- D-pad فعلي.
- زر Emergency Stop فعلي.
- صفحة Telemetry أو رسوم حية.

لذلك خيار External Cloud Backend مذكور في الشرح فقط، وليس مشروعًا قابلًا للتشغيل.

### 5. Local Web Server وSPIFFS وTunneling وAccess Point غير منفذة
النص طلب خيارًا محليًا داخل ESP32، مع HTML/CSS/JS في SPIFFS، وإمكانية Tunnel، ثم وضع AP عند انقطاع الإنترنت. لا يوجد في الكود:

- `WebServer` أو `ESPAsyncWebServer`.
- `SPIFFS.begin()`.
- ملفات واجهة داخلية.
- `WiFi.softAP()`.
- منطق اكتشاف انقطاع السحابة والتحويل التلقائي.
- Tunnel configuration.

الموجود هو وصف هندسي فقط.

### 6. Telemetry لا تذهب إلى السحابة
كود ESP32 يطبع السطر التالي عبر Serial فقط:

```cpp
Serial.printf("angle=%.2f output=%.2f\\n",input,output);
```

لا يوجد نشر MQTT أو WebSocket، ولا حقول كاملة تشمل المسافة والاتجاه وحالة النظام، ولا واجهة تعرضها.

### 7. HC-SR04 غير موجود في الكود
يوجد شرح جيد في README وBlueprint، لكن لا توجد:

- تعريفات `TRIG_PIN` و`ECHO_PIN` في firmware.
- قراءة `pulseIn` أو بديل غير حاجب.
- تحويل Echo level.
- حساب مسافة.
- شرط أقل من متر.
- تعديل `setpoint` عند أمر Forward.

إذن Auto-Stop الآمن لم يُنفذ، بل هو إجراء موثق فقط.

### 8. IR والريموت غير منفذين
`IR_PIN` معرف في الكود، و`pinMode(IR_PIN, INPUT)` موجود في Arduino، لكن لا توجد:

- مكتبة `IRremote` في `libraries`.
- كائن استقبال IR.
- قراءة كود.
- جدول أكواد فعلي للريموت.
- timeout للكود الأخير.
- ربط أزرار Up/Down/Left/Right/Mode/Stop بالتحكم.

ملف receiver يشرح ما يجب فعله، لكنه لا ينفذه.

### 9. FD650 والشاشة غير منفذين
لا يوجد Driver للشاشة ولا اختبار بروتوكول DAT/CLK. وهذا صحيح من ناحية عدم التخمين، لكنه يعني أن عرض المسافة أو حالة النظام على الشاشة لم يُنفذ.

### 10. سلوك LEDs لا يطابق النص بالكامل
النص طلب:

- LEDs الوسطى ثابتة عند الاتزان.
- وميض متتابع عند الحركة للأمام.
- وميض متتابع عكسي عند الحركة للخلف.
- وميض سريع للكل عند خطر السقوط.

كود Arduino الحالي يجعل LEDs ثابتة وفق شروط الزاوية فقط في `indicators()`. لا يوجد timer أو sequence أو animation. كود ESP32 لا يستدعي LEDs أصلًا. لذلك الوظيفة جزئية وليست مطابقة للمواصفة.

### 11. قراءة MPU6050 غير مكتملة
في Arduino:

```cpp
Wire.beginTransmission(0x68);
Wire.write(0x3B);
```

لكن لا توجد تهيئة فعلية لـ MPU6050، ولا `MPU6050 mpu`، ولا `initialize()`، ولا فحص اتصال، ولا offsets، ولا DMP، ولا دمج gyro/accelerometer. كما أن القراءة هي أول قيمتي Accelerometer وتُحوّل بـ `map()` إلى زاوية تقريبية، وليست زاوية ميل موثوقة.

في ESP32:

```cpp
double readAngle() { return 0; }
```

وهذا يعني أن PID في ESP32 لا يستقبل قراءة حقيقية إطلاقًا.

### 12. دوال الحركة والاتجاه ناقصة
النص المرفق يحتوي على `turnLeft()` و`turnRight()` ويدعم `L` و`R`. كود Arduino المنشور لا يحتوي هاتين الدالتين؛ يدعم عمليًا `F` و`B`، وأي أمر آخر يعيد `setpoint` إلى صفر. كود ESP32 لا يقرأ `command` ولا يدعم F/B/L/R/S فعليًا.

### 13. ملف Wokwi ليس محاكاة كاملة وصالحته ناقصة
`simulation/wokwi/diagram.json` المنشور يحتوي على:

- Arduino Uno.
- MPU6050.
- أربع LEDs.

ولا يحتوي على L298N أو محركات أو HC-SR04 أو IR أو ESP32 أو شاشة. كذلك توجد توصيلات غير صالحة حرفيًا مثل:

```json
"uno:{pin}"
```

لأن `{pin}` لم يُستبدل برقم فعلي. ولا توجد مقاومات LEDs في الرسم. لذلك الملف ليس محاكاة كاملة للمشروع، وقد لا يعمل في Wokwi كما هو.

### 14. تناقض في أرجل ESP32
في `hardware/PINOUT_AND_POWER_AR.md` مكتوب أن LEDs في ESP32 هي:

```text
GPIO13, 12, 14, 27
```

لكن `ESP32Standalone.ino` يعرفها هكذا:

```cpp
LED_1 = 4
LED_2 = 16
LED_3 = 17
LED_4 = 23
```

كما أن GPIO14 وGPIO27 مستخدمان في جدول الوثائق كـ PWM للمحركات، وبالتالي جدول الوثائق القديم يسبب تعارضًا إن استُخدم حرفيًا. يجب اعتماد جدول واحد نهائي قبل التوصيل.

### 15. تناقض في ترتيب IN1 وIN2
النص المرفق يستخدم:

```cpp
IN1_PIN 7
IN2_PIN 6
```

بينما الكود المنشور يستخدم:

```cpp
IN1_PIN 6
IN2_PIN 7
```

قد يكون هذا مجرد تبديل مقصود بسبب اتجاه المحرك، لكنه غير موثق كتغيير، ويجب حسمه بتجربة اتجاه العجلات وتثبيته في جدول واحد.

### 16. مكتبة Xbox غير موجودة
النص الأصلي يذكر:

```cpp
#include <XboxSeriesXControllerESP32.h>
```

هذه المكتبة غير موجودة في المشروع، ولا يوجد استخدام فعلي لذراع PS1/Xbox أو كود pairing أو استقبال. الموجود حاليًا هو Serial command concept فقط.

### 17. مخططات TeX مبسطة
ملفا TeX موجودان، لكنهما يقدمان مخططين مفاهيميين مختصرين. لا يعكسان كل تفاصيل النص المرفق، ومنها HC-SR04، UART level shifting، MODE_PIN، Local AP، tunnel، SPIFFS، وتسلسل LEDs. لذلك هما موجودان كمرجع بصري، وليسا رسومات تنفيذية كاملة للتوصيل.

## ما هو جاهز للانتقال إلى مرحلة التطوير الجديدة

البنية التنظيمية والتوثيق الأساسي جاهزان كقاعدة عمل. كذلك توجد مكتبات I2Cdev وMPU6050 وPID_v1 وLMotorController، وجداول أولية للأرجل، وهيكلان منفصلان لـ Arduino وESP32.

## ما يجب إنجازه قبل اعتبار المتطلبات مكتملة

1. تحديد هل المطلوب كود موحد `#ifdef` أم ملفان مستقلان رسميًا.
2. بناء قراءة MPU6050 حقيقية مع تهيئة ومعايرة وفلترة.
3. تنفيذ ESP32 Bridge وUART وتبديل MODE_PIN.
4. تنفيذ HC-SR04 ومنطق تعديل setpoint.
5. تنفيذ IRremote والتقاط الأكواد الفعلية.
6. حسم بروتوكول FD650 أو إبقاؤه خارج النسخة التنفيذية بوضوح.
7. إعادة اختيار Pinout واحد بلا تعارض وتحديث جميع الملفات به.
8. تنفيذ LEDs المتسلسلة والمؤقتة على Arduino وESP32.
9. اختيار Cloud Backend وإنشاء Dashboard فعلي، أو إعلان أن الـ Dashboard مؤجل.
10. بناء Wokwi صحيح بمكونات فعلية وتوصيلات رقمية حقيقية، أو تسميته مخططًا مفاهيميًا فقط.
11. تشغيل compile test لكل Firmware على اللوحة المستهدفة.
12. اختبار السقوط، فقد Wi‑Fi، فقد remote، اقتراب عائق، وزر الإيقاف.

## الحكم النهائي

الرابط الحالي **منظم وموثق بصورة جيدة**، لكنه ليس بعدُ تنفيذًا كاملًا لكل ما ورد في النص. أكبر فجوة هي أن Dashboard، ESP32 Bridge، HC-SR04، IR، FD650، وضع `#ifdef`، قراءة ESP32 للحساس، ومحاكاة Wokwi الكاملة غير منفذة أو غير مكتملة. لذلك لا ينبغي البدء بتجربة hardware على أساس أن كل الوظائف المذكورة تعمل؛ ينبغي اعتبار الرابط الحالي **مخططًا منظمًا ونسخة أساس Prototype** إلى أن تُنفذ البنود أعلاه.

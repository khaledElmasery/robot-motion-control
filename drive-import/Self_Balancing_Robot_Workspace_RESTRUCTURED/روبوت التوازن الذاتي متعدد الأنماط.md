# روبوت التوازن الذاتي متعدد الأنماط

## ملخص المشروع

هذا المشروع روبوت بعجلتين يحافظ على وضعه الرأسي باستخدام حساس MPU6050، وخوارزمية PID، ودرايفر L298N، مع أربع طرق تشغيل: تشغيل Arduino عبر USB، Arduino مع ESP32 كجسر لاسلكي، Arduino مستقل، وESP32 مستقل بعد نقل الأسلاك فعليًا. توجد طبقة تحكم محلية للطوارئ، وطبقة Cloud Backend اختيارية للتحكم عبر الإنترنت، وقياس Telemetry حي، وحساس HC-SR04 لمنع الاصطدام، ومؤشرات LEDs، ومدخل IR من لوحة receiver قديمة، مع شاشة FD650 اختيارية لا تُفعّل قبل قياس بروتوكولها.

> **مبدأ السلامة:** مسار الاتزان هو الأولوية: `MPU6050 → زاوية الميل → PID → PWM/اتجاه → L298N → المحركات`. لا يجوز أن يؤدي Web Dashboard أو Wi‑Fi أو IR أو أي طلب سحابي إلى حجب قراءة الحساس أو حلقة PID. اختبر العجلات مرفوعة، وافصل البطارية قبل تغيير أي سلك.

## ما الذي يفعله النظام

عند التشغيل يهيئ المتحكم I2C وMPU6050 وPID ودرايفر المحركات. يقرأ زاوية الميل دوريًا بمرشح تكميلي يجمع accelerometer وgyro. يحسب PID قيمة تصحيح بين `-255` و`255` ثم يحدد الاتجاه وPWM للمحركين. أمر `F` يجعل setpoint موجبًا قليلًا، و`B` يجعله سالبًا، بينما `L` و`R` يضيفان فرق دوران محدودًا، و`S` يوقف الحركة المطلوبة مع بقاء PID مسؤولًا عن الاتزان.

يقرأ HC-SR04 المسافة. إذا كانت المسافة أقل من 100 سم وكان الأمر أماميًا، يُلغى setpoint الأمامي ويُستخدم setpoint وقوف/رجوع بسيط بدل قطع المحركات فجأة. إذا تجاوز الميل حد الخطر، تُوقف المحركات ويومض كل LED. عند الاتزان تضيء LED2 وLED3، وعند الحركة تتحرك الإضاءة بالتتابع.

كل أمر اتصال ينتهي تلقائيًا بعد ثانية إذا لم يصل أمر جديد. هذا يمنع استمرار الحركة عند فقد الهاتف أو Wi‑Fi أو Dashboard.

## الأنماط الأربعة

### 1. USB Direct — Arduino

Arduino هو العقل الوحيد. يتصل الكمبيوتر عبر USB، ويقرأ أوامر Serial، وMPU6050، وHC-SR04، ويقود L298N. هذا هو أول نمط يجب اختباره، ولا يحتاج ESP32 أو إنترنت.

### 2. Arduino + ESP32 Bridge

Arduino يظل مسؤولًا عن الحساس وPID والمحركات. ESP32 يتصل بالشبكة أو يعمل بوضع الطوارئ، ويستقبل أوامر Dashboard عبر Cloud Backend أو الواجهة المحلية، ثم يرسل أحرف `F/B/L/R/S` عبر UART محمي بمحول مستويات. يرسل Arduino Telemetry بصيغة نصية، ويعيد ESP32 نشرها إلى Backend.

### 3. Arduino Standalone

Arduino يعمل دون أي اتصال خارجي، ويحافظ على setpoint الصفر. هذا النمط مخصص لاختبار الاتزان قبل إضافة أي اتصال أو ريموت.

### 4. ESP32 Standalone

تُفصل أسلاك Arduino فعليًا أولًا، ثم تُنقل إلى جدول ESP32. يقرأ ESP32 MPU6050، يشغل PID وLEDC PWM، يدير HC-SR04 وIR والاتصال، ويعرض Dashboard محليًا عند الحاجة. لا تشغّل هذا النمط مع نفس توصيلات Arduino في الوقت نفسه.

### Arduino Uno

| L298N ENA | D5 | ENA/PWM |

| L298N IN3/IN4 | D8/D9 | اتجاه الجانب الأيمن |

| UART Bridge | Serial USB/D0-D1 حسب التصميم | استخدم مستوى 5V↔3.3V |

### الطاقة والأرضي

البطارية تذهب إلى مدخل الطاقة في L298N عبر مفتاح فصل. لا تدخل البطارية إلى Arduino أو ESP32 أو MPU6050. استخدم Buck Converter مناسبًا، واربط GND بين الوحدات عند استخدام Bridge. لا تجعل L298N مصدرًا غير موثوق لـESP32. عند استخدام محركين في كل جانب، يوصل محركا الجانب بالتوازي فقط إذا كان تيار L298N مناسبًا؛ لا تستخدم التوالي.

## الاتصال السحابي والمحلي

### Cloud Backend

يوجد Backend مستقل في `cloud-backend/` مبني على Node.js بدون حزم خارجية. يوفر:

- `GET /` لواجهة Dashboard.
- `GET /api/state` لقراءة آخر Telemetry والأمر الحالي.
- `GET /api/stream` لبث Telemetry عبر Server-Sent Events.
- `POST /api/command` لاستقبال D-pad.
- `POST /api/telemetry` لاستقبال Telemetry من ESP32.
- `GET /api/device/command` ليجلب ESP32 الأمر الحالي.

يحمي الـBackend المسارات بمتغير `CONTROL_TOKEN`. لا تنشره للعامة قبل وضع HTTPS، وتغيير الرمز، وتحديد معدل الطلبات، ووضع سياسة للمستخدمين. "أي شخص يملك الرابط" ليس إعدادًا آمنًا افتراضيًا.

### Local Web Server والطوارئ

ESP32 يفتح AP باسم `BalanceBot-Setup` عند تعذر السحابة أو عند اختيار الوضع المحلي. صفحة `data/index.html` هي نسخة طوارئ صغيرة، ويمكن رفعها إلى SPIFFS/LittleFS حسب بيئة البناء. لا تعتمد على الصفحة المحلية لمعالجة عدد كبير من المستخدمين؛ المسار الحركي أهم من الواجهة.

## تشغيل المشروع خطوة بخطوة

1. افصل البطارية واختر نمطًا واحدًا.
2. طابق التوصيلات مع الجداول أعلاه، وتأكد من GND ومقسم الجهد والمقاومات.
3. ابدأ باختبار MPU6050 فقط، ثم نفّذ معايرة وهو مستوٍ وثابت وسجل offsets.
4. ارفع Firmware Arduino أو Unified Firmware بعد اختيار board والـlibraries.
5. ارفع العجلات عن الأرض واختبر اتجاه كل محرك بقدرة منخفضة.
6. اختبر PID بقيم `Ki=0` و`Kd=0` ثم Kp، وبعدها Kd، ثم Ki.
7. أضف HC-SR04 واختبر أن الاقتراب من عائق لا يقطع الاتزان بعنف.
8. أضف LEDs، ثم IR بعد التقاط الأكواد، ثم Bridge.
9. شغّل Backend: `node cloud-backend/server.js`، ثم افتح Dashboard.
10. عرّف `CLOUD_BASE_URL` و`CONTROL_TOKEN` في ESP32، واختبر Telemetry والأوامر.
11. اختبر فقد السحابة؛ يجب أن يتوقف الأمر بعد المهلة أو يتحول إلى AP محلي.
12. لا تبدأ اختبار البطارية الكامل إلا بعد نجاح قائمة الفحص.

## تشغيل Backend

```bash
cd cloud-backend
CONTROL_TOKEN=change-me PORT=8080 node server.js
```

افتح `http://localhost:8080/`. في ESP32 استخدم عنوان الخادم القابل للوصول من شبكة الروبوت. لا تستخدم `localhost` داخل ESP32 إلا إذا كان Backend يعمل على نفس الجهاز، وهذا غير معتاد.

## بروتوكول الأوامر وTelemetry

الأوامر المسموح بها هي `F`, `B`, `L`, `R`, `S`. Telemetry النصية من Arduino هي:

```text
TEL angle=-0.12 output=3.40 distance=142.0 command=S mode=arduino
```

وTelemetry HTTP هي JSON:

```json
{"angle":-0.12,"output":3.40,"distance":142.0,"command":"S","mode":"bridge","uptime":12345}
```

## IR وFD650

طرف IR في لوحة SUPER GOLD X3 SG-555 لا يعني أن أكواد الريموت معروفة. صِل VCC/GND/IR بعد قياس الجهد، وثبّت مكتبة IRremote، وسجل كل زر من Serial Monitor، ثم اربط Up بـF وDown بـB وLeft بـL وRight بـR وStop بـS. لا تستخدم أكواد ريموت تخمينية.

وجود FD650 لا يكفي لمعرفة بروتوكول الشاشة. افحص DAT وCLK وADD/5V وGND بــdatasheet أو Logic Analyzer. لا تضف Driver نهائيًا ولا توصل الشاشة إلى GPIO قبل التحقق من الجهد والتوقيت.

## حدود النسخة

الكود والتوثيق قابلان للبناء كنقطة تطوير، لكن المعايرة النهائية، اتجاه المحركات، سلوك الهيكل، تيار البطارية، أكواد IR، بروتوكول FD650، واختبار الحمل السحابي تحتاج عتادًا حقيقيًا. لا يوجد Software يستطيع إثبات سلامة روبوت ميكانيكي دون اختبار فيزيائي.

# محاكاة Wokwi واختبارات firmware

## الحالة

هذا مشروع محاكاة **مبدئي** مولّد من خريطة الأرجل الموجودة في `src/main.cpp`، وليس نسخة مؤكدة من مخطط المستخدم الفعلي. الصورة الوحيدة التي وصلت للمراجعة كانت لقطة شاشة للكود في VS Code، لا مخططًا كهربائيًا. لذلك لم يمكن مطابقة مخطط أو قياس مقسم الجهد الفعلي.

### نتيجة التحقق في 2026-10-01

- **نجح محليًا:** `wokwi-cli lint simulation/wokwi`؛ بناء PlatformIO للبيئات `uno`, `esp32_bridge`, `esp32_standalone`؛ اختبارا Python الذاتي والوحدوي؛ فحص صياغة ملفات YAML؛ و`py_compile`. هذه الفحوص لا تشغّل firmware على محاكي.
- **لم تُشغّل سيناريوهات Wokwi عبر CLI:** المشغّل `run_tests.py` يحتاج متغير البيئة السري `WOKWI_CLI_TOKEN`، ولم يكن مضبوطًا في بيئة المهمة. لم يُقرأ أو يُسجّل أي رمز.
- **محاولة المتصفح العام لم تنتج نتيجة محاكاة:** حُمّل firmware المنشور والمخطط المؤقت داخل مشروع Wokwi جديد غير محفوظ، ثم بقيت الواجهة تعرض `Build server load` لأكثر من 92 ثانية؛ أُلغيت المحاولة. لم يثبت اكتمال ترجمة السحابة أو بدء المحاكاة، لذلك لا يوجد سيناريو Wokwi ناجح مسجل.
- لم يُستخدم زرا `Save` أو `Share`، ولا يوجد رابط دائم للمشروع المؤقت.

لا تسجّل الوثائق نجاحًا لمحاكاة فعلية قبل تشغيل `run_tests.py` وفحص مخرجات كل سيناريو. ملفات السيناريو الحالية **مسودات اختبار غير منفذة**، وليست دليلًا على اجتياز firmware.

## النطاق المتوقع للاختبار

المحاكاة **مقترحة لاختبار** منطق Uno البرمجي، واختلافات الأرجل، والتعامل مع الأوامر والحساسات المتاحة في Wokwi. تتضمن مسودات السيناريوهات: تقدمًا مع مسار خالٍ، منع التقدم عند عائق أقرب من 15cm، منع التقدم عند فصل Echo، تغيير مستوى السرعة ورسالة PWM، إيقاف المحركات عند فقد نبضات `Z`، واختبار أمر الميل `^` بعد تحريك MPU6050 الافتراضي. لم تُعتمد صحة هذه التوقعات بالتشغيل بعد.

تستخدم `diagram.json` نموذج L298N مجتمعيًا من GitHub مع LEDs على المخارج بدل المحركات الحقيقية. هذا النموذج يتيح فحص إشارات الاتجاه والتمكين فقط؛ ولا يحاكي عزم المحرك أو تيار التعثر أو هبوط مصدر الطاقة أو التصادم أو حركة الهيكل. كما أن المشروع لا يختبر اتصال Bluetooth Classic SPP من يد التحكم ولا المفتاح الفعلي متعدد الأقطاب. لا تستطيع المحاكاة إثبات صحة قيمة المقسم الفعلية أو لحامه أو حدود الجهد في لوحة ESP32.

## تشغيل الاختبارات

1. ثبّت PlatformIO Core وWokwi CLI. تنص وثائق Wokwi الرسمية على أن تشغيل CLI/السيناريوهات يحتاج Wokwi CI token.
2. جهّز متغير `WOKWI_CLI_TOKEN` في بيئة التنفيذ بطريقة آمنة. لا تضعه في Git، ولا ترسله في رسالة أو تكتبه في ملف المشروع.
3. من جذر المستودع شغّل:

   ```bash
   python3 simulation/wokwi/run_tests.py
   ```

   يبني المشغل بيئة Uno أولًا، ثم ينشئ مخططات مؤقتة لحالات المسافة المختلفة وفصل Echo، ويشغّل سيناريوهات YAML الستة. تُحذف المخططات المؤقتة آليًا.

4. راجع مخرجات كل سيناريو. أي فشل في البناء أو انتظار الرسائل التسلسلية أو قيمة pin يجب تسجيله، ومعالجته قبل ادعاء نجاح المحاكاة.

## مقارنة المخطط الحقيقي

قبل اعتبار الرسم ممثلًا للروبوت، طابق مخططًا كهربائيًا فعليًا يرسله المستخدم مع [دليل التوصيلات](../../docs/WIRING_AND_HARDWARE.md)، خصوصًا طرفي `TX→1` و`RX←0`، مقسم الجهد، الأرضي المشترك، تغذية L298N، ومواضع مفتاح الوضع. النموذج الحالي يفترض توصيلات المستودع فقط، ولا يعوض عن مراجعة مخطط الجهاز الحقيقي أو قياس الجهود.
